# Telegram-бот для поиска подселения в Минске — MVP-каркас (Этап 2)

Этот каркас уже умеет:
- `/start` — регистрация пользователя, главное меню.
- `/profile` — пошаговое заполнение анкеты (пол, возраст, бюджет, районы,
  тип жилья, к кому подселиться, животные/курение/привычки, работа/учёба,
  о себе) и сохранение в SQLite.
- Просмотр анкеты через кнопку «👤 Моя анкета».

Поиска жилья (парсер Kufar, matching, карточки объявлений) пока нет —
это Этапы 3–5.

## Куда что класть

Просто распакуй всё в одну папку — структура уже готова:

```
project/
├── bot.py
├── config.py
├── requirements.txt
├── .env.example
├── .gitignore
├── handlers/       (start.py, profile.py)
├── keyboards/       (main.py, inline.py)
├── states/           (profile.py)
├── database/           (models.py, database.py, crud.py)
└── utils/                (helpers.py)
```

## Установка

```bash
cd project
python3 -m venv .venv
source .venv/bin/activate      # на Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

## Настройка

1. Скопируй `.env.example` в `.env`:
   ```bash
   cp .env.example .env
   ```
2. Открой `.env` и впиши:
   - `BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather) (команда `/newbot`).
   - `ADMIN_ID` — твой Telegram ID числом (узнать можно у [@userinfobot](https://t.me/userinfobot)).
   - `DB_PATH` — можно оставить `bot.db` (файл создастся сам рядом с `bot.py`).

Пример `.env`:
```
BOT_TOKEN=123456789:AAExampleTokenFromBotFather1234567890
ADMIN_ID=123456789
DB_PATH=bot.db
```

## Запуск

```bash
python3 bot.py
```

Если всё настроено верно, увидишь в логах `Бот запускается...` — значит
бот вышел в поллинг и готов принимать команды в Telegram.

При первом запуске файл `bot.db` создастся автоматически со всеми
таблицами (`users`, `profiles`, `profile_districts`, `listings`,
`favorites` — последние две пока пустые, заполнятся на Этапе 3–4).

## Что проверить у себя

1. Отправь боту `/start` → должно прийти приветствие и меню с кнопками.
2. Нажми «👤 Моя анкета» → бот скажет, что анкеты нет, и предложит `/profile`.
3. Отправь `/profile` → пройди все шаги анкеты до конца.
4. После заполнения снова нажми «👤 Моя анкета» → должна показаться
   сохранённая анкета.
5. Отправь `/profile` ещё раз и заполни по-другому → старая анкета должна
   замениться новой (не задваиваться).

## Известные ограничения MVP (уже учтены в архитектуре, не баги)

- FSM хранится в памяти (`MemoryStorage`) — при перезапуске бота незавершённое
  заполнение анкеты обнулится. Уже сохранённые анкеты в БД не теряются.
- Миграций БД нет (`Base.metadata.create_all`) — если поменяешь модели в
  `database/models.py`, для применения изменений на существующей базе
  проще всего удалить `bot.db` и перезапустить бота (данные потеряются).
  Alembic можно добавить позже, когда схема стабилизируется.
- `/update` и `/stats` для администратора появятся на Этапе 6.

## Этап 4–5 — matching и поиск в боте (сделано)

Кнопка «🏠 Найти жильё» теперь работает по-настоящему:
1. Бот берёт районы из твоей анкеты.
2. Идёт на Kufar через `sources/kufar.py` (по одному запросу на район,
   без нарушения `robots.txt`).
3. Сохраняет найденное в БД (`services/listings.py`).
4. Прогоняет через фильтр и рейтинг (`services/matching.py`) — жёстко
   отсекается только то, что точно дороже бюджета; остальное сортируется
   по проценту соответствия.
5. Показывает карточки одну за другой с кнопками ⬅️/➡️, ❤️ (сохранить в
   избранное — уже работает по-настоящему, не заглушка) и 🔗 на само
   объявление.

### Что нужно сделать у себя

1. Зависимости не менялись с прошлого раза — если уже стоят, ничего
   доустанавливать не надо.
2. **Если у тебя уже есть файл `bot.db`** — удали его перед запуском:
   схема снова поменялась (у `price` в объявлениях убрали обязательность,
   иначе бот падал бы на любой «Договорной» цене — нашёл это в тестах,
   уже исправлено). Миграций всё ещё нет, поэтому проще всего:
   ```bash
   rm bot.db
   ```
3. Запусти бота: `python3 bot.py`
4. В Telegram: `/start` → `/profile` (если анкеты ещё нет или хочешь
   пересоздать) → нажми **🏠 Найти жильё**.
5. Бот напишет «Ищу подходящие варианты…», через несколько секунд должна
   появиться первая карточка с процентом соответствия. Полистай ⬅️➡️,
   попробуй ❤️ (нажми ещё раз на ту же карточку — должно переключиться на
   «убрать из сохранённых»).

Если результатов ноль, или бот падает с ошибкой, или карточка выглядит
криво (обрезанный текст, мусор в заголовке) — пришли мне, что вышло, я
это не мог до конца проверить сам: в моей песочнице Kufar отвечает 403
(похоже, из-за дата-центрового IP), так что реальный прогон запроса к
Kufar возможен только с твоей стороны.

### Известные грубые места (сознательно, не баги)

- Заголовок карточки — черновая эвристика (обрезанный слипшийся текст),
  see `sources/kufar.py`. Как увидим реальный вывод — доточим.
- Курс BYN→USD захардкожен приблизительно в `services/matching.py`
  (`BYN_TO_USD_RATE`). Обновляй вручную при сильных отклонениях от жизни.
- Тип жилья (комната/подселение) и пол соседей определяются по ключевым
  словам в тексте — это эвристика, не точные данные, поэтому участвуют
  только в рейтинге (`⭐ %`), не в жёстком отборе.

## Правки по твоей обратной связи (после первого реального теста)

Спасибо за реальный вывод карточки — по нему поправил:

- **Убрал мусор** «Позвонить Сравнить» / «calculator» — раньше он просто
  подмешивался в текст объявления, теперь чистится в одном месте
  (`KufarSource._clean_text`, `sources/kufar.py`).
- **Убрал дублирование** — раньше заголовок и описание были почти
  одинаковым текстом (оба — весь слипшийся блок). Теперь описание
  показывает только то, что идёт ПОСЛЕ заголовка (`services/formatting.py`).
- **Добавил фото** — если у объявления нашлась картинка (`<img>` внутри
  карточки на Kufar), бот теперь присылает её как `send_photo` с текстом
  в подписи, а не отдельным текстовым сообщением. Если картинки нет —
  как и раньше, просто текстом. Из-за этого пагинация (⬅️➡️) больше не
  редактирует сообщение на месте, а удаляет старую карточку и присылает
  новую — Telegram не даёт превратить фото-сообщение в текстовое через
  `edit_*` и наоборот.

**Не стал делать сейчас — дата публикации.** У меня нет достоверных
данных, где именно на странице Kufar она лежит (я не видел реальную
разметку, только текст карточки-ссылки) — гадать по тексту не хочу,
рискую подсунуть неверную дату. Если хочешь, можем разобраться отдельно:
открой в браузере DevTools на любой карточке `re.kufar.by/l/minsk/...`
и посмотри, есть ли рядом с объявлением что-то вроде «сегодня», «вчера»,
конкретная дата — если да, пришли мне, как это выглядит в HTML (Ctrl+Shift+C
→ клик по этому тексту → посмотри на подсвеченный тег), и я добавлю

## Этап 6 — админка (сделано)

Добавил `/update` и `/stats`, доступны только тебе (по `ADMIN_ID` из `.env`
— остальным бот на эти команды просто не ответит, как будто их не существует).

- **`/update`** — обходит все 9 официальных районов Минска сразу (не
  только те, что в чьей-то анкете) и складывает найденное в БД. Одно
  сообщение "Обновляю..." → через ~10-15 секунд (9 запросов с паузой
  между ними, как и раньше — без нарушения `robots.txt`) → "Готово,
  обработано N объявлений".
- **`/stats`** — пользователи всего, активные за 7 дней, анкеты,
  объявления в базе, избранное.

Про «активных за 7 дней» — важная деталь: раньше `updated_at` у
пользователя обновлялся только если реально менялись `username`/
`first_name`, то есть почти никогда после первого `/start`. Метрика была
бы бессмысленной. Поправил — теперь `updated_at` трогается при каждом
обращении к боту, независимо от того, поменялось что-то в профиле или
нет.

Заодно поймал и убрал `DeprecationWarning` от `datetime.utcnow()` — у
тебя Python 3.14, там это уже официально помечено к удалению в будущем.
Проверил тестом с `-W error::DeprecationWarning`, чтобы быть уверенным,
что нигде больше не осталось.

### Что нужно сделать у себя

БД снова не менялась. Просто:
```bash
python3 bot.py
```
В Telegram (с того аккаунта, чей ID указан как `ADMIN_ID` в `.env`)
отправь `/update`, потом `/stats`.

## Раздел «Сохранённые» (сделано)

Кнопка «❤️ Сохранённые» теперь реально показывает то, что ты сохранял —
переиспользует ту же карточку/пагинацию, что и поиск (это тот же
`SearchSession.browsing`, просто список объявлений собирается не через
Kufar+matching, а прямо из таблицы `favorites`).

Одна деталь, которую специально добавил сверх минимума: если убрать ❤️
с карточки **находясь именно в разделе «Сохранённые»** — она сразу
пропадает из текущего списка (не просто меняется кнопка на «Сохранить»
обратно). Если убрать последнюю — бот вежливо сообщит, что сохранённых
больше нет, и вернёт в меню. При обычном поиске (не в «Сохранённых»)
поведение как было: сняли ❤️ — карточка остаётся в списке, просто кнопка
меняется обратно на «Сохранить».

### Что нужно сделать у себя

время поиска, потом зайди в «❤️ Сохранённые» и убери одно — должно сразу
исчезнуть из списка, не дожидаясь повторного открытия раздела.

## Version 1.1 — прозрачный score + быстрый поиск (сделано)

По итогам продуктового аудита — два изменения:

### Карточка объясняет процент

Раньше «⭐ 95%» просто появлялось из ниоткуда. Теперь под ним — чек-лист:
```
⭐ Подходит вам: 95%
✅ Бюджет · ✅ Район · ⚠️ Пол соседей не уточнён · ✅ Тип жилья
```
Это те же веса, что считались и раньше (`services/matching.py`), просто
теперь `explain_match()` возвращает не голое число, а разбивку по
критериям — `match_score()` остался как обёртка для мест, где нужно
только число. Обрати внимание на формулировку «не уточнён», а не
«не подходит» — там, где наша эвристика не смогла ничего подтвердить,
честнее показать неопределённость, чем выдумывать однозначный минус.

Заодно (это давно откладывалось) — довёл до конца извлечение адреса из
слипшегося текста Kufar: в шапке карточки теперь именно улица
(«Газеты Правда пр, 22»), а не обрывок «действие+адрес+начало описания».
Нашёл по пути тонкий баг в первой версии регулярки: символьный класс
`[А-Яа-яЁё]` не различает регистр *внутри* одного слова, поэтому склеенные
без пробела фрагменты вроде «МинскСтахановская» съедались целиком как одно
слово. Сузил класс для середины слова до строчных букв — заглавная сама
стала границей. Проверено на всех реальных примерах, что накопились за
разведку.

### Быстрый поиск без анкеты

Если нажать «🏠 Найти жильё» без заполненной анкеты — раньше бот просто
отправлял на `/profile`. Теперь предлагает выбор:

```
⚡ Быстрый поиск       👤 Заполнить анкету
```

Быстрый поиск — это 3 вопроса (бюджет / районы / кого ищешь в соседи) и
сразу результаты, без сохранения анкеты в БД. Технически — `QuickProfile`
в `services/matching.py`: лёгкий dataclass с теми же именами полей, что
использует matching-логика, поэтому `match_listing`/`explain_match`
работают с ним точно так же, как с настоящим `Profile` — без отдельной
ветки кода.

Карточки в «Сохранённых» теперь **без** процента подходящести — раньше
score там пересчитывался на лету против текущей анкеты, что для объявлений
из быстрого поиска (анкеты вообще нет) было бы либо ошибкой, либо
бессмысленным числом. Явное решение: в контексте «уже сохранил» процент
не нужен, там важен сам факт, что понравилось.

Также добавил «📋 X из Y» на каждую карточку — теперь видно, сколько всего
найдено/сохранено, не только в момент открытия раздела, а на протяжении
всего пролистывания.

### Что нужно сделать у себя

БД не менялась. `python3 bot.py`. Попробуй:
1. Без анкеты нажать «🏠 Найти жильё» — должен появиться выбор быстрый/анкета.
2. Пройти быстрый поиск — 3 шага, сразу карточки с чек-листом.
3. Проверить обычный поиск (если анкета уже есть) — чек-лист там тоже
   должен появиться.
4. Проверить «❤️ Сохранённые» — там теперь счётчик сверху и карточки без
   процента.

## «⚙️ Настройки» (сделано)

Раньше кнопка честно писала «будет добавлено позже» — теперь работает:

- **✏️ Изменить анкету** — то же самое, что `/profile`, просто доступно
  из меню, не только командой.
- **🗑 Удалить анкету** — с подтверждением («Точно?» / Да / Отмена).
  Удаляется только анкета — избранное (❤️) не трогается, это специально
  проверено тестом (см. ниже).

Технически `crud.delete_profile()` использует тот же приём, что и
`upsert_profile()` раньше: явный `DELETE` по districts вместо обхода
ORM-коллекции — иначе рисковали снова поймать `MissingGreenlet` в async-сессии
(это тот самый баг с самого начала проекта, теперь паттерн закреплён и
переиспользуется, а не повторяется вручную).
